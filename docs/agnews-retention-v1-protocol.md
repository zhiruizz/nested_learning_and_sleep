# AG News class-incremental retention v1 - frozen preregistration

**Status at the preregistration commit: main training has not started and official test contents have not been decoded.** The user authorized the experiment and publication. Root and an independent reviewer checked the implementation before launch. The main CLI stops the whole block on failure and has no resume or automatic retry path.

## Question and scope

Test whether a real Llama 3.2 3B model, after learning two AG News classes, can adapt to two disjoint classes while retaining the first pair, and whether CMS plus the defined Sleep procedure differs from ordinary adaptation or a labeled-replay compute proxy. This is a small, local class-incremental study, not a reproduction of the Sleep paper and not a general natural-language continual-learning benchmark.

Classes are fixed by source label: old = World (0), Sports (1); new = Business (2), Sci/Tech (3). Input articles come only from the pinned official training split for all training and calibration roles. The official test split remains sealed until every main run is complete and sealed.

## Data and answer format

The training source is `fancyzhx/ag_news`, revision `eb185aade064a813bc0b7f42de02595523103ca4`; pinned train parquet SHA-256 `fc508d6d9868594e3da960a8cfeb63ab5a4746598b93428c224397080c1f52ee`. The tokenizer/model source is the existing local ModelScope Llama 3.2 3B asset. ModelScope dataset metadata returned HTTP 404; no dependency was installed. The train-role pack is `agnews-train-roles-v1.json`, SHA-256 `7b5169daadcf7d4ccaefc9d0bb79f1a4eef92fc275fae0c3a7d593e06b7e9e59`.

Selection normalizes article text with NFKC, whitespace collapse, and casefold; removes duplicate normalized text and conflicting-label groups; then removes duplicate tokenized prompt prefixes. The preparation code selected 2,048 candidates per class before token-prefix deduplication and froze 2,048 records total: per class, DEV train 128, DEV calibration 64, MAIN train 256, and MAIN calibration 64. The prep summary reports 151 normalized duplicate rows removed and 22 conflicting normalized-text groups dropped; the final pack records 22 normalized conflict groups and zero prompt-prefix conflict groups. Record IDs and prompt hashes are unique across all four roles; prompt boundaries and the 96-token article cap were checked. Final prompts contain 18 prefix tokens including BOS, at most 96 article tokens, and a 3-token `Answer:` cue, for lengths 38-117. The prompt contains no answer completion.

Every response is exactly two generated tokens: shared marker ` tag` followed by one class-code token; no EOS is trained. The class-code mapping is a fixed seed-specific permutation of four one-token codes (`red`, `blue`, `green`, `gold`), shared across old/new and train/calibration within each seed. Evaluate full-vocabulary two-token greedy exact match and NLL, plus marker accuracy and four-code candidate accuracy; do not restrict greedy decoding to candidate tokens. The four-code candidate chance level is 25%.

The pack precomputes 512 foundation batches and 256 primary new-task batches per seed, each batch size 4 with two examples from each of the phase's two classes. DEV uses seed 1907 and DEV-only roles; MAIN seeds are 17, 29, and 43 and use MAIN-only roles. The schedules are deterministic, hashed, and do not draw from calibration roles. Sampling is with replacement, so repeated prompts across steps and occasional within-batch duplicates are possible; report schedule hashes and actual repeat counts. Four Sleep pools per seed contain 24 train prompts each, exactly six per class: the first 16 are GKD prompts `[0,2,3,1,1,3,2,0]` repeated twice, the last 8 are LTI prompts `[0,2,1,3]` repeated twice. Thus each Sleep event is 50/50 old/new by prompt count.

Extra replay is frozen as two consecutive passes through the matching event's 24-prompt pool, grouped by four: 12 batches/event, one example/class/batch. Its derived schedule hashes appear in the preregistration lock. Labels remain separate `class_id` metadata; no answer is appended to a prompt record. Extra replay advances the same CMS optimizer clocks, while its primary data cursor stays fixed. Therefore its level-16 boundaries may occur at different primary steps from CMS; it is an augmented labeled-rehearsal treatment, not an identical optimizer schedule or isolated Sleep-mechanism comparison.

## Main experiment

Run three seeds (17, 29, 43), serially, with the same pinned model and `(0.005,0.01)` LR pair selected by DEV. For each seed, train one 512-update old-class foundation at batch size 4, then fork all five arms from the exact same foundation state and optimizer/RNG initialization. Within a seed, arms use the same precomputed 256-batch primary new-task schedule; replay uses its separate frozen train-only schedule and does not advance the primary cursor. Save and report all schedules and hashes.

The five arms are:

1. **Frozen:** no new-task optimizer updates.
2. **SFT:** 256 primary new-task updates with controller periods `[1,1]`.
3. **CMS:** 256 primary updates with periods `[4,16]`.
4. **CMS+Sleep:** same 256 primary updates and CMS periods; at primary steps 64, 128, 192, 256 run one Sleep transaction using that event's fixed 24-prompt train-only pool: 16 GKD and 8 LTI updates, `dream_tokens=2`, no Dream.
5. **CMS+extra-replay:** same CMS primary updates plus 12 batch-size-4 labeled replay updates at each of the same four boundaries (48 additional SGD updates per seed), with one example from each class in every replay batch. Replay uses only MAIN train records and the frozen replay schedule.

At a simultaneous CMS due boundary, operate on a candidate clone: apply slow level-1 proposal first, construct the Sleep teacher from that slow-updated candidate, pass the level-0 proposal prospectively to Sleep without pre-applying it, then commit model and controller atomically only if fixed engineering checks pass (finite values, exact parameter scope/frozen-base invariants, valid nonzero receiver gradients). Consume each proposal exactly once on commit. A failed engineering check discards the candidate, leaves the original model/controller/pending state intact, stops that run, and is not retried. No development/test metric may gate a Sleep commit or select a trajectory.

Save checkpoints at foundation and primary cursors 0, 64, 128, 192, 256. Boundary checkpoints bind mutable adapters, execution/routing state, CMS pending sums/counts, Python/NumPy/Torch CPU/CUDA RNG, current primary/replay cursor, and data/config/source hashes. They are outside the Sleep transaction and do not contain an in-flight Sleep teacher/Adam. The private DEV fixture separately checks in-flight Sleep optimizer recovery. The main CLI has no resume entry point. Any failure ends the whole block, saves the available live mutable/controller/RNG diagnostic state, and leaves test sealed; there is no ghost restore or automatic retry. Completed boundary checkpoints are read-only evaluation artifacts; actual restore consistency was checked in the separate real-3B DEV fixture. Use one 3,600-second fixed hard cap for the complete 15-run main block; no extension. If any run fails or the cap expires, stop and do not unseal official test. No run replacement, seed substitution, LR adjustment, or post hoc extra steps.

Expected work if all runs complete: 3 foundations x 512 = 1,536 SGD updates; SFT/CMS/CMS+Sleep/CMS+replay primary new wake = 3 x 4 x 256 = 3,072 SGD updates; replay adds 3 x 48 = 144 SGD updates. Total wake/foundation/replay SGD = 4,752 updates; Sleep adds 3 x 4 x (16+8) = 288 Sleep-Adam updates. Report the actual count by arm, not only this planned total.

## Interpretation and references

All three seeds and every checkpoint remain in the report, including acquisition failures. The same 512 official-test articles are reused across seeds; these are not 1,536 independent test articles. Public pretrained corpora may contain AG News articles, and random output codes do not establish that articles were unseen. Fixed-length two-token greedy EM equals the conjunction of marker argmax and gold-marker-conditioned class argmax in this causal model; candidate-code accuracy is only an auxiliary constrained metric. No EOS or longer response is evaluated.

The study was motivated by [Sleep v2](https://arxiv.org/abs/2606.03979v2), [Nested Learning v1](https://arxiv.org/abs/2512.24695v1), and the diagnostics in [obekt/HOPE-nested-learning](https://github.com/obekt/HOPE-nested-learning/tree/599244e65fedf26f4db9844beb631c3dbca41188). Upstream code was not copied; an MIT badge without a license file was insufficient to assume permission. This last-MLP architecture, truncated-article four-code task, partial GKD/LTI without Dream, small data budget and approximate replay control do not reproduce either paper or upstream WikiText/copying scores.

Model weights, private mutable checkpoints, raw source data and tokenized examples remain under ignored outputs and are not released. Consult the original asset terms; repository licensing does not cover those third-party assets.
